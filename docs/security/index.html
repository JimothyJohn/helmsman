For IT and security

Security

A controller on your network decides what your machine does. This page explains who can see it, who can change it, and how you can check every claim here for yourself.

Read the source

Access and control

Nobody walks in

  • Sign-in for everything

    Reading programs, live values or the I/O map needs a sign-in, and so does every change. A request without one is refused before it reaches anything.

  • Roles and approval

    Operators, engineers and integrators each get what their role allows. A change that can affect an output needs an engineer, and a site policy can only make these rules stricter.

  • Guessing gets locked out

    Wrong passwords lock the account for a time that doubles with each miss, up to an hour, and the whole controller slows down a flood of attempts across accounts.

  • Sessions end

    A sign-in lasts an hour at most and ends after 15 minutes unused. Disabling an account or changing its password ends its sessions too.

  • A complete record

    Every change, approval and sign-in goes into an append-only audit log with the person and the time.

  • Existing PLCs stay untouched

    Helmsman can read tags from the PLCs you already run. It has no way to write to them.

On the wire

Interception and injection

  • Encrypted by default

    The controller serves its editor and API over HTTPS (TLS 1.2 and 1.3) with a certificate it makes on first start. You compare its fingerprint once, and from then on a stand-in cannot pass as your controller. Plain HTTP from another machine is sent to HTTPS or refused.

  • Sessions stay out of reach

    The sign-in is held in a cookie that scripts on the page cannot read, and the editor's pages only run scripts the controller itself lists.

  • Documents are only read

    Specs, drawings and exported programs you hand to Helmsman are treated as untrusted. They are read as text and never run, and nothing written in them can widen what Helmsman is allowed to reach.

  • Strict input checks

    Every request and every device reply is size-limited and checked field by field. Anything malformed is dropped before it is used.

How it is built

Small and checkable

Helmsman is written in a memory-safe language, which rules out whole classes of attack such as buffer overflows. The few places that must talk to the operating system directly are kept in one small module and reviewed line by line.

It depends on few outside libraries, and each new one is reviewed before it comes in. Every change runs the full test suite, including interoperability tests against real protocol stacks, before it ships.

There is no cloud in the control path. Programs keep running if the internet goes away; only the programming help waits for it to come back.

Credentials

No default passwords

A controller ships with no account and no password. You create the accounts, and passwords are stored only as salted, slow hashes. Passwords and PINs never appear in a log.

The Skipper

Any change to a Skipper node, such as a new program, a stop or new settings, needs the node's key. Its live values can be read by anyone on the same network, so keep it on the machine network.

Open source

Look for yourself

Every line of Helmsman is public under Apache 2.0, including the tests that hold it to the claims on this page. Read the code, run the tests, or have your own team review it.
